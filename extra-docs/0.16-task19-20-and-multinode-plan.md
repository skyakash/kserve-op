## Task #19 — Label a node for the `localmodelnode-agent` DaemonSet (✅ done)

### Current state

The DaemonSet ships with `nodeSelector: kserve/localmodel=worker`. The label is applied per worker node — one command per node.

### What the agent does

`kserve-localmodelnode-agent` is the per-node component of the local-model caching subsystem:

- One agent Pod runs on every node the cluster admin opts in by applying the label
- The agent manages node-local storage (default path `/var/lib/kserve/local-models`) where pre-fetched model weights live
- The agent mounts/unmounts PVs that point at that storage
- The agent reports to `kserve-localmodel-controller-manager` (a single Deployment in the operator namespace) about which models the node currently has cached

The split: **controller decides _what_ to cache and _where_; agents do the actual fetch and storage management.**

### Apply the label

Single-node Docker Desktop:
```bash
kubectl label node docker-desktop kserve/localmodel=worker
```

Multinode kind (typical: label each worker, leave control-plane alone):
```bash
kubectl label node desktop-worker  kserve/localmodel=worker
kubectl label node desktop-worker2 kserve/localmodel=worker
```

Verification:
```bash
kubectl get ds -n <operator-ns> kserve-localmodelnode-agent
# Expected: DESIRED == labeled-worker-count, CURRENT == DESIRED, READY == DESIRED
```

### LocalModelCache (✅ validated end-to-end on multinode kind)

**Validation flow that actually works:**

1. Cluster admin creates a `LocalModelNodeGroup` with a static PV template that uses **the same storageClassName for both PV and PVC** (a real bug we hit — see the storage-class footnote)
2. Cluster admin creates a `LocalModelCache` with `sourceModelUri: gs://...` (or `pvc://...` for air-gapped — see offline sample)
3. `localmodel-controller-manager` reconciles → spawns one download Job per labeled worker node → each Job's storage-initializer fetches the model into the node-local PV
4. Cache status reaches `copies.available == labeled-worker-count`, `nodeStatus.<node>: NodeDownloaded`
5. User deploys an InferenceService with `storageUri` **exactly equal to the cache's sourceModelUri** — KServe's defaults webhook matches by URI and auto-rewrites the predictor to mount the cache PVC instead of pulling from the source
6. Predictor pod has `kserve-pvc-source -> sklearn-iris-cache-default-worker` mount; inference returns predictions

**What ships in `06-sample-model/`:**

| File | Purpose |
|---|---|
| `localmodelcache-nodegroup.yaml` | LocalModelNodeGroup with PV template + nodeAffinity matching `kserve/localmodel=worker` |
| `localmodelcache.yaml` | Online LocalModelCache (gs://) for the iris model |
| `localmodelcache-isvc.yaml` | ISVC with the same gs:// URI (defaults webhook auto-injects cache PVC) |
| `localmodelcache-offline-source-pvc.yaml` | Source PVC for the air-gapped variant (with side-load instructions in the YAML header) |
| `localmodelcache-offline.yaml` | Offline LocalModelCache (pvc://) — points at the source PVC |
| `localmodelcache-offline-isvc.yaml` | ISVC for the offline cache (same pvc:// URI) |

## Multinode kind is **now the required** test environment for LocalModelCache

The single-node Docker Desktop cluster cannot exercise the per-node placement logic that is the whole reason `LocalModelNodeGroup` exists. Validating LocalModelCache on a single node tells us essentially nothing about the multinode behavior.

### What multinode adds that single-node can't

| Aspect | Single-node Docker Desktop | 2-3 node kind (this branch's test env) |
|---|---|---|
| Image-pin fix actually deploys clean | ✅ Sufficient | ✅ Same |
| `localmodelnode-agent` Pod runs without crash when labeled | ✅ Sufficient | ✅ Same |
| **`LocalModelNodeGroup` per-node placement** | ❌ Impossible | ✅ **Real validation here** |
| `nodeStatus` shows multiple nodes with `NodeDownloaded` | ❌ Always 1 node | ✅ Confirms multi-replica fan-out |
| Cache fetched once per node into per-node PV | ❌ Always 1 PV | ✅ One PV per labeled worker |
| Iris standard path | ✅ Already passing | ✅ Same |
| llmisvc smoke (CR → Deployment + HTTPRoute created) | ✅ Either works | ✅ Either works |

### What multinode does **not** help with

- LLM memory/CPU requirements — total Docker Desktop RAM is fixed; splitting across nodes means each gets less, not more
- Gateway API CRD prereqs — same regardless of topology
- The core fixes (image pin, CRD permission) — architecture-independent
- **Hostpath fsGroup permission limitation** (see below — same on Docker Desktop and kind)

### Setting up the kind cluster

`kind` ≥ v0.31 (installed via `brew install kind` on macOS, or release binary on Linux). Save this as `kind-multinode.yaml`:

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

Then:

```bash
kind create cluster --name desktop --config kind-multinode.yaml
kubectl get nodes
# Expected: 3 nodes total — <name>-control-plane + 2 workers
```

`kind-multinode.yaml` is shipped at `extra-docs/kind-multinode.yaml` for convenience.

## Known limitation — hostpath + fsGroup chown

The `kserve/storage-initializer` runs as non-root (UID 1000). Its volumeMount is satisfied by a hostpath-based PV (path `/var/lib/kserve/local-models` on each node). On both Docker Desktop and kind, **kubelet does not honor `fsGroup` chown on hostpath volumes**, so the directory stays root-owned and the storage-initializer's first write fails with `Permission denied`.

This is a known Kubernetes/hostpath limitation, **not** a KServe or operator bug. On real production clusters using proper CSI drivers (EBS, GCEPD, Azure Disk, OpenShift's storage classes), fsGroup chown works correctly and this step is not needed.

### Workaround (required on Docker Desktop and kind)

Run a one-shot privileged Pod per labeled worker that creates the directory with the right ownership. Single-node:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: chown-localmodel-host
  namespace: default
spec:
  restartPolicy: Never
  nodeSelector: { kserve/localmodel: worker }
  containers:
    - name: c
      image: busybox:1.36
      command: ["sh","-c","mkdir -p /host/var/lib/kserve/local-models && chown -R 1000:1000 /host/var/lib/kserve/local-models"]
      securityContext: { privileged: true }
      volumeMounts: [{ name: host, mountPath: /host }]
  volumes:
    - { name: host, hostPath: { path: /, type: Directory } }
EOF
kubectl wait --for=jsonpath='{.status.phase}'=Succeeded pod/chown-localmodel-host -n default --timeout=60s
kubectl delete pod chown-localmodel-host -n default
```

Multinode: repeat with `nodeSelector: { kubernetes.io/hostname: <node-name> }` for each labeled worker.

**Production cluster:** skip this step entirely. Use a storage class with proper fsGroup support.

## Storage class footnote (real bug we hit)

The `LocalModelNodeGroup` sample originally specified `storageClassName: hostpath` only on the PV template, not on the PVC template. The PVC then defaulted to the cluster default storage class (`standard` on kind), so PV and PVC ended up in different classes and never bound — the download Jobs sat waiting forever on `PVC is not bound`.

**Fixed in `localmodelcache-nodegroup-sample.yaml.tmpl`** by pinning `storageClassName: hostpath` on both PV and PVC. The pinned value matches the Docker Desktop default and is also available on kind.

## When to use single-node Docker Desktop vs. multinode kind

The honest breakdown:

| What we want to validate | Single-node Docker Desktop | 2–3 node kind |
|---|---|---|
| Initial operator deploy + standard iris ISVC | ✅ Sufficient (already proven) | ✅ Same |
| LocalModelCache mechanism reaches `NodeDownloaded` | ✅ Works (one node) | ✅ Works (multi-node) |
| `LocalModelNodeGroup` placement across nodes | ❌ Cannot test | ✅ Real validation |
| llmisvc smoke (CR → Deployment + HTTPRoute) | ✅ Either works | ✅ Either works |
| Real LLM inference | Depends on model size, not topology | Same |
| Hostpath chown limitation | Required | Required |

**Recommendation:** for any LocalModelCache work on this branch, use multinode kind. For other validation, either works.
