## Task #19 — Label a node for the `localmodelnode-agent` DaemonSet

### Current state

```
$ kubectl get ds -n servewell
NAME                          DESIRED   CURRENT   READY   NODE SELECTOR
kserve-localmodelnode-agent   0         0         0       kserve/localmodel=worker
```

The DaemonSet ships with a `nodeSelector: kserve/localmodel=worker`. No node in a fresh cluster carries that label, so `desired=0` and nothing schedules. The KServeRawMode CR still reaches `Ready` because there are no pending pods to wait for — but the LocalModelCache feature is unusable until at least one node is labeled.

### What the agent does

`kserve-localmodelnode-agent` is the per-node component of the local-model caching subsystem:

- One agent Pod runs on every node the cluster admin opts in by applying the label
- The agent manages node-local storage (default path under `/mnt/models/...`) where pre-fetched model weights live
- The agent mounts/unmounts PVs that point at that storage
- The agent reports to `kserve-localmodel-controller-manager` (a single Deployment in `servewell`) about which models the node currently has cached

The split: **controller decides _what_ to cache and _where_; agents do the actual fetch and storage management.**

### The fix

One command for the single-node Docker Desktop:

```bash
kubectl label node docker-desktop kserve/localmodel=worker
```

Verification:

```bash
kubectl get ds -n servewell kserve-localmodelnode-agent
# Expected: DESIRED=1 CURRENT=1 READY=1

kubectl get po -n servewell -l control-plane=kserve-localmodelnode-agent
# Expected: one Pod, 1/1 Running
```

For a multi-node production cluster, the admin labels only the nodes intended to host the cache — typically the storage- or GPU-heavy ones.

## Task #20 — Iris-style smoke tests for `LocalModelCache` and `LLMInferenceService`

Iris is the template: ship a sample YAML alongside the operator package and document a one-page test procedure. We replicate that shape for each new subsystem.

### LocalModelCache test (depends on #19)

**Validation flow:**

1. Cluster admin creates a `LocalModelCache` CR pointing at a model (small, well-known — initially the same iris model already shipped)
2. `localmodel-controller-manager` reconciles → selects a worker node (matching the label from #19) → tells the agent to fetch
3. Agent downloads weights to node-local storage, creates a PV/PVC bound to that path
4. User deploys an InferenceService with `storageUri: pvc://<cached-pvc>/...`
5. Inference returns predictions identical to the standard iris test

**What ships:**

| File (input template) | Purpose |
|---|---|
| `kserve-raw-base/localmodelcache-sample.yaml.tmpl` | `LocalModelCache` + companion `LocalModelNodeGroup` for the iris model |
| `kserve-raw-base/localmodelcache-isvc-sample.yaml.tmpl` | InferenceService consuming the cache |

Generator stage 6 copies these into `06-sample-model/` next to the existing `sklearn-iris.yaml`. QUICK_START.md gets a Step 6c subsection mirroring Step 6: `kubectl apply` → wait on `LocalModelCache.status.copies` → `kubectl apply` ISVC → `curl` predict → expect `{"predictions":[1]}`.

**Practical concerns:**

- The agent's default storage path is under `/mnt/models/...`. Need to verify the chosen cluster's nodes can write there.
- Model fetch over `gs://` requires the same internet access the existing iris test already needs — same constraint, not a new one.

### LLMInferenceService test (independent of #19, much heavier)

Real LLM inference needs an LLM, which needs real memory and compute. Honest options:

| Approach | Size needed | Realism | Recommended for |
|---|---|---|---|
| **Smoke only** — apply CR, verify controller wires the resources | none | Low | **First pass** |
| `TinyLlama-1.1B` actual inference | ~2 GB RAM, CPU OK | Medium | Phase 2 |
| `gpt2` (124M) | ~500 MB | Medium-low | If TinyLlama doesn't fit |
| Production-sized LLM | GPU required | High | Not in scope |

**First pass: pure smoke**

- Apply an `LLMInferenceService` CR with a placeholder model reference
- Verify the operator reconciles it: `Deployment` is created, `Service` is created, `HTTPRoute` (Gateway API) is created
- Skip the actual inference call
- This validates the llmisvc controller is doing its job, independent of whether the LLM can answer

**Additional prerequisite** the llmisvc path needs:

- **Gateway API CRDs** (`gateway.networking.k8s.io`). The controller's logs reference `*v1alpha2.InferencePool` and `gateway-inference-extension.yaml` — llmisvc routes traffic via Gateway API, not Services. We install Gateway API CRDs as a cluster prereq, similar to cert-manager.

## When to use single-node Docker Desktop vs. multinode kind

The honest breakdown:

| What we want to validate | Single-node Docker Desktop | 2–3 node kind cluster |
|---|---|---|
| Image-pin fix actually deploys clean | ✅ Done (v604, 0 restarts) | ✅ Same |
| `localmodelnode-agent` runs without crash when labeled | ✅ Sufficient | ✅ Same |
| **`LocalModelNodeGroup` placement (model A on node X, model B on node Y)** | ❌ Impossible — only 1 node | ✅ **This is where multinode pays off** |
| What happens when a labeled node disappears | ❌ Trivial / not testable | ✅ Realistic |
| Iris standard path | ✅ Already passing | ✅ Same |
| llmisvc smoke (CR → Deployment + HTTPRoute created) | ✅ Either works | ✅ Either works |
| Real LLM inference | Depends on model size, not topology | Depends on model size, not topology |

### What multinode does **not** help with

- LLM memory/CPU requirements — total Docker Desktop RAM is fixed; splitting across nodes means each gets less, not more
- Gateway API CRD prereqs — same regardless of topology
- The fixes we already shipped (image pin, CRD permission) — architecture-independent

### Practical cost of multinode kind on Docker Desktop

- Each kind "node" is a container; on a Mac with 16–24 GB allocated to Docker Desktop, 3 nodes fit comfortably
- Switching kubectl context, re-installing cert-manager + OLM + v604 — ~15 minutes of one-time overhead
- You can keep both: the Docker Desktop k8s context for quick iteration, kind for the multi-node-specific validation
- kind setup is essentially:
  ```yaml
  # kind-multinode.yaml
  kind: Cluster
  apiVersion: kind.x-k8s.io/v1alpha4
  nodes:
    - role: control-plane
    - role: worker
    - role: worker
  ```
  ```bash
  kind create cluster --name kserve-multi --config kind-multinode.yaml
  ```

## When to reset the cluster (Cluster lifecycle plan)

Decision rules for the remaining work:

| Phase | Cluster needed | Action |
|---|---|---|
| **Now → Task #19** | Current single-node, **no reset** | Just `kubectl label node docker-desktop kserve/localmodel=worker`. The fix doesn't change embedded manifests; v604 still applies. |
| **#19 verification settles cleanly** | Same cluster, **no reset** | Confirm DS pod is `1/1 Running`. Move on. |
| **LocalModelCache smoke (first pass)** | Same cluster, **no reset** | Apply sample, validate on single-node. This won't prove `LocalModelNodeGroup` placement but proves the controller-agent flow. |
| **`LocalModelNodeGroup` real validation** | **Reset → recreate as multinode kind** | This is the natural switch point. Tear down Docker Desktop k8s, `kind create cluster --config kind-multinode.yaml`, reinstall cert-manager + OLM + v604, re-run the smoke. |
| **LLMInferenceService smoke-only** | Either cluster — multinode is fine to keep | No need to revert if you're already on kind. |
| **Real LLM inference** | Whichever has enough RAM | Decide based on model choice. |

**Bottom line:** the next cluster reset is at the LocalModelNodeGroup step — not before. Everything from "label the node" through "first LocalModelCache smoke" can run on the cluster you have now.

## Single-cluster cheatsheet for the next steps

For Task #19 — no reset needed:

```bash
# Label
kubectl label node docker-desktop kserve/localmodel=worker

# Verify DaemonSet schedules
kubectl get ds -n servewell kserve-localmodelnode-agent
kubectl get po -n servewell -l control-plane=kserve-localmodelnode-agent

# If the Pod doesn't go 1/1 Ready in ~60s, gather:
kubectl logs -n servewell -l control-plane=kserve-localmodelnode-agent --tail=50
kubectl describe po -n servewell -l control-plane=kserve-localmodelnode-agent
```

For switching to multinode kind (when we get to LocalModelNodeGroup):

```bash
# Stop using Docker Desktop k8s (optional: just switch kubectl context)
# kind installs into a separate context — no need to disable Docker Desktop k8s

# Create the kind config
cat > /tmp/kind-multinode.yaml <<EOF
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
EOF

# Create
kind create cluster --name kserve-multi --config /tmp/kind-multinode.yaml

# Verify
kubectl get nodes
# Expect 3 nodes: kserve-multi-control-plane, kserve-multi-worker, kserve-multi-worker2

# Then redo the whole deploy: cert-manager → OLM → namespaces → setup-credentials → operator-sdk run bundle v604-bundle
# Same commands as before, just on the new cluster context.
```
