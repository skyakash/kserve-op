### T03 — `install.sh` with `KSERVE_NAMESPACE=servewell` env var override + iris

**Status:** ❌ **FAIL — real bug found**

**Goal:** Validate install.sh's namespace-override path (Design C without the operator). Same as T02 but with `KSERVE_NAMESPACE=servewell`.

**Steps:**

```bash
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.17.2/cert-manager.yaml
kubectl wait --for=condition=Ready pods --all -n cert-manager --timeout=180s

cd p-kserve-raw && KSERVE_NAMESPACE=servewell bash install.sh
```

**What happened:**

install.sh applied stages 1–3 (CRDs, RBAC, Core), then stage 4 (ClusterServingRuntimes) failed with:

```
Error from server (InternalError): failed calling webhook
  "clusterservingruntime.kserve-webhook-server.validator":
  Post "https://kserve-webhook-server-service.servewell.svc:443/.../validate-...":
  tls: failed to verify certificate:
  x509: certificate is valid for kserve-webhook-server-service.kserve.svc,
        not kserve-webhook-server-service.servewell.svc
```

**Root cause analysis:**

| Resource | Field | After install.sh applied | Expected (for `servewell`) | Result |
|---|---|---|---|---|
| `ValidatingWebhookConfiguration` `inferenceservice.serving.kserve.io` | `clientConfig.service.namespace` | **`servewell`** ✓ | `servewell` | ✅ rewritten |
| `Certificate` `serving-cert` | `spec.dnsNames` | **`kserve-webhook-server-service.kserve.svc`** ✗ | `kserve-webhook-server-service.servewell.svc` | ❌ NOT rewritten |
| `Certificate` `llmisvc-serving-cert` | `spec.dnsNames` | **`llmisvc-webhook-server-service.kserve.svc`** ✗ | `llmisvc-webhook-server-service.servewell.svc` | ❌ NOT rewritten |

Result: kubelet routes the webhook call to the right Service (in `servewell`), but the Service's TLS cert has the wrong SAN (`*.kserve.svc`). TLS handshake fails. Stage 4 cannot apply ClusterServingRuntimes (which the webhook validates), and the install is broken.

**The sed regex limitation:**

```bash
sed "s|^\([[:space:]]*\)namespace: kserve$|\1namespace: ${KSERVE_NAMESPACE}|"
```

This anchored regex only matches `[whitespace]namespace: kserve$` line patterns. It does **not** match:
- `dnsNames: [..., "kserve-webhook-server-service.kserve.svc"]` (DNS pattern embedded in a list element)
- `commonName: kserve-webhook-server-service.kserve.svc` (DNS pattern in a scalar)
- `subjects[].namespace: kserve` for ClusterRoleBindings (probably affected too — not explicitly verified)

The operator's `apply.go` has a structured YAML walk that handles all of these kinds correctly. `install.sh` does not.

**Severity:** **High**. Documentation in [`kserve-raw-base/README.md.tmpl`](../kserve-raw-base/README.md.tmpl) and [`QUICK_START.md` Part C](../QUICK_START.md#part-c-alternative--offline--air-gapped-model-test) advertises `KSERVE_NAMESPACE` as a working override; this test proves it is not. The default `KSERVE_NAMESPACE=kserve` path works (T02) because no rewriting is needed. ANY override breaks.

**This was a latent gap noted in `gaps-and-observations.md`** ("Sed-based rewrite in install.sh.tmpl is less safe") — T03 turned it into a confirmed bug.

**Recommended fix options:**

1. **Replace the sed function with a Python YAML walk** that mirrors `apply.go`'s structural logic: rewrite ClusterRoleBinding subjects, WebhookConfiguration service namespaces, Certificate `dnsNames`/`commonName`, cert-manager `inject-ca-from` annotations.
2. **Remove the `KSERVE_NAMESPACE` override entirely** from install.sh and document that custom namespaces require the operator-based path (OLM bundle or operator-deployment.yaml). The DEFAULT `kserve` namespace would still work via install.sh.
3. **Bake the rewrite at extract time** in `generate-kserve-raw.sh` instead of at install time — let the user pick the namespace at build time. But this loses the runtime-flexibility install.sh aims for.

Option 1 is the right long-term fix. Option 2 is the safest short-term mitigation if Option 1 won't ship soon.

**Documentation gaps observed:**

- [`gaps-and-observations.md`](gaps-and-observations.md) line "Sed-based rewrite in install.sh.tmpl is less safe" says it "works in practice." T03 contradicts this — needs to be updated from "less safe" to "**broken for custom namespaces**" with severity High.
- The install.sh's own comment block (`install.sh.tmpl` lines around `rewrite_ns`) acknowledges the regex is anchored to avoid touching identifiers, but doesn't warn that **structured fields like Certificate `dnsNames` will silently NOT be rewritten** — so the resulting install is broken for non-default namespaces.
- [`kserve-raw-base/README.md.tmpl`](../kserve-raw-base/README.md.tmpl)'s "Choosing the KServe namespace" section advertises a feature that doesn't work. Misleading.

**No regression test for this scenario before T03** — this is the first time `install.sh + KSERVE_NAMESPACE=<custom>` has been exercised on the 0.16 source (and possibly on any source — the gap was documented but not validated).

### T13 — LocalModelCache **online** (`gs://`) on multinode (2 workers)

**Status:** ✅ PASS (with re-chown retry; see Observations)

**Goal:** Validate the NEW 0.16 LocalModelCache feature end-to-end on multinode — per-node fan-out of a single model, automatic PVC injection into matching ISVCs, inference from local cache (no internet at predictor startup).

**Context note — chown is a local-cluster workaround only:**

The kserve/storage-initializer runs as UID 1000 (non-root). On **production clusters** with proper CSI drivers (EBS, GCE PD, Azure Disk, OpenShift LocalVolume, Ceph RBD, etc.), `fsGroup: 1000` in the Job pod's securityContext correctly chowns the mounted volume — no manual step needed. On **dev clusters using hostpath-backed PVs** (Docker Desktop's `hostpath`, kind's `standard`/local-path-provisioner, minikube), kubelet's fsGroup chown does NOT propagate to the host directory, so the storage-initializer's first write fails with `Permission denied`. The chown Pods we use here are a workaround for THIS specific dev-cluster limitation — production users skip the chown entirely. Documented in [`extra-docs/LOCAL-MODEL-CACHE-GUIDE.md`](LOCAL-MODEL-CACHE-GUIDE.md#prerequisites).

**Steps:**

kubectl label node desktop-worker2 kserve/localmodel=worker

# - Initial chown before LocalModelCache exists
for n in desktop-worker desktop-worker2; do
  kubectl apply -f - <<EOF
apiVersion: v1
kind: Pod
metadata: { name: chown-$n, namespace: default }

kubectl apply -f 06-sample-model/localmodelcache.yaml

**Observations during test — chown ordering issue:**

This is a **newly-discovered** wrinkle on the local-cluster chown workaround that wasn't documented in the LOCAL-MODEL-CACHE-GUIDE before T13:

1. The chown Pod runs at time T0 — makes `/var/lib/kserve/local-models/` 1000:1000 ✅
2. Apply NodeGroup + LocalModelCache CRs at T1

**Bug #1 — `pvc://` is not a supported `sourceModelUri` scheme for LocalModelCache:**

The KServe storage-initializer supports `pvc://` for **standard InferenceServices** (T07 PASSED for this — `pvc://` ISVC works perfectly). In that path the storage-initializer mounts the source PVC at one path and copies into `/mnt/models`. But for **LocalModelCache**, the storage-initializer is invoked with `(src_uri, dest_path)` where `dest_path = /mnt/models` is the cache PVC. There's no separate source PVC mount in the Job pod's spec for the cache's `sourceModelUri`; the initializer is expected to download from the URI scheme directly. **`pvc://` as a source scheme is not implemented** for this code path.

Supported schemes for `LocalModelCache.sourceModelUri` (per the error message): `gs://`, `s3://`, `file://`, `http(s)://`, `hf://`.

**Our sample YAML (`localmodelcache-offline-sample.yaml.tmpl`) is fundamentally wrong.** It assumes the same `pvc://` semantics as standard ISVCs, which is not how LocalModelCache works.

**Real offline patterns for LocalModelCache** (any of these would work in air-gap):
- `s3://` pointing at an **internal Minio** in the customer's cluster
- `http(s)://` pointing at an internal HTTP server hosting model files
- `hf://` pointing at an **internal HuggingFace mirror**

For purely-side-loaded scenarios (the original intent of our offline sample), **the right answer is to skip LocalModelCache entirely** and use a **direct `pvc://` ISVC** (T07 pattern). LocalModelCache's value is "cache a remote model on each node so cold starts are fast" — if you already have the model side-loaded on a PVC, the LocalModelCache layer adds no value; you just point your ISVC at that PVC directly.

**Bug #2 — ConfigMap `localModel.defaultJobImage` not honored:**

Verified state in cluster:

| | Value |
|---|---|
| `kubectl get cm inferenceservice-config -o jsonpath={.data.localModel}` → `defaultJobImage` | `kserve/storage-initializer:v0.16.0` (pinned correctly) ✓ |
| Embedded `04-kserve-core/kserve-core.yaml` `storage-initializer:latest` occurrences | 0 (all rewritten to v0.16.0) ✓ |
| Embedded `04-kserve-core/kserve-core.yaml` `storage-initializer:v0.16.0` occurrences | 5 ✓ |
| **Running Job pod's container image** | `kserve/storage-initializer:latest` ❌ |

Despite the ConfigMap being correctly patched in both the generator's output AND the live cluster, the localmodel-controller spawns download Jobs with the **`:latest`** tag — not the configured `defaultJobImage`. This suggests the controller is **not reading `localModel.defaultJobImage` from the ConfigMap at all** — it's using a hardcoded default in the binary, OR an env var, OR a different config source.

This is a real KServe operator-pipeline issue: our pin doesn't actually take effect at runtime.

**What we DID validate (still useful):**

### T15 — LocalModelCache cleanup path

**Status:** ❌ **FAIL — upstream KServe v0.16.0 bug in ISVC finalizer cleanup**

**Goal:** Verify that deleting `ISVC → LocalModelCache → LocalModelNodeGroup` in the documented order leaves no orphan PVs/PVCs/Jobs. The cleanup path is critical for any production environment where users update models or decommission caches.

**Setup (worked):**

Reused T13's online flow (gs://) since T14 proved the offline pvc:// variant is unsupported:

1. Standard deploy + chown + apply NodeGroup + Cache → cache reaches `NodeDownloaded` on both workers ✅
2. Apply ISVC `sklearn-iris-cached` → ISVC reaches Ready, predictor pod has cache PVC injected ✅

**Cleanup attempt (failed at step 1):**

```bash
# Step 1: Delete the ISVC (should remove finalizer, then disappear)
kubectl delete isvc sklearn-iris-cached -n default
# kubectl returns "deleted" immediately, but the resource stays.
```

**ISVC stays in `Terminating` state with `deletionTimestamp` set but `finalizers: ["inferenceservice.finalizers"]` not clearing.** 9+ minutes later, the ISVC still exists; PVs/PVCs/Jobs are all still around because the chain is blocked.

**Root cause (from controller logs):**

```
"Deleting external resources","InferenceService":"sklearn-iris-cached"   ← controller starts cleanup
"LocalModelCache found","model":"sklearn-iris-cache",...,"isvc":"sklearn-iris-cached"  ← defaulting webhook re-injects PVC annotation
"validate update","name":"sklearn-iris-cached"                          ← validating webhook fires
ERROR Reconciler error: admission webhook denied the request:
  update rejected: deploymentMode cannot be changed from 'Standard' to 'RawDeployment'
```

The sequence:
1. Controller attempts to remove its finalizer (an UPDATE to `metadata.finalizers`)
2. **KServe's defaulting (mutating) webhook fires on every ISVC update**, including finalizer-only updates. It re-evaluates the LocalModelCache match and tries to re-inject `internal.serving.kserve.io/localmodel-pvc-name` and the deploymentMode default.
3. After mutation, KServe's validating webhook fires. The old object has some baseline deploymentMode value (`Standard`), and the mutated new object asserts a different one (`RawDeployment`). The validator's "immutable field" rule rejects the change.
4. The update fails → finalizer not removed → the controller re-queues → **infinite loop**

**This is an upstream KServe v0.16.0 defect, not a defect in our operator pipeline.** The mutating webhook should be a no-op for finalizer-only updates; alternatively, the defaulter shouldn't re-evaluate LocalModelCache matching on every reconcile.

**Workaround options (none used during T15):**

1. Scale down `kserve-controller-manager` deployment → patch finalizers to `[]` → scale back up
2. Edit the `inferenceservice.serving.kserve.io` validating webhook config to set `failurePolicy: Ignore`
3. `kubectl delete --grace-period=0 --force` (won't actually work — finalizers block force-delete too)

**What we DID validate (the parts that worked):**

| Check | Result |
|---|---|
| Cache + ISVC fully Ready before cleanup test | ✅ |
| PV/PVC topology: 2 PVs (`-download` in `kserve-localmodel-jobs`, `-default` in `default`), 2 PVCs | ✅ |
| 2 `LocalModelNode` CRs auto-created (one per labeled worker) | ✅ |
| `kubectl delete isvc` is accepted (resource enters Terminating) | ✅ |
| Finalizer-removal blocked → cleanup chain never proceeds | ❌ |
| No orphan checks possible (resources never actually deleted) | n/a — couldn't reach this stage |

**Severity:** **High.** This is a real production-impacting bug:
- Any user trying to clean up a LocalModelCache-using ISVC will hit this
- Manual workarounds require cluster-admin privileges (patching finalizers, editing webhook configs)
- A naive `kubectl delete -A` script will hang indefinitely
- The bug is in upstream KServe v0.16.0; our operator's code isn't involved

**Possible test cases discovered:**

- **T15a (suggested):** Same scenario but delete the ISVC FIRST, BEFORE applying enable-ingress.sh / other operations. Confirms the deploymentMode race isn't created by ingress flipping.
- **T15b (suggested):** Skip the ISVC entirely — just create Cache, then delete Cache. Does the LocalModelCache CR's own finalizer behave correctly?
- **T15c (suggested):** Bypass the webhook (admin workaround above) and verify the underlying cleanup logic is correct once the finalizer is forced.

**Documentation gaps observed:**

### T15-RETEST — Stuck-ISVC cleanup workaround after Issue #3 docs update

**Status:** ✅ PASS (docs corrected mid-test)

**Goal:** Validate the GUIDE's documented "Stuck ISVC cleanup" workaround actually works end-to-end. Reproduce the T15 finalizer hang, then run the documented commands.

**Setup (after cluster reset):** cert-manager + KServe + chown helper + NodeGroup + LocalModelCache populated + ISVC Ready. Standard online-flow prereqs identical to T13-RETEST.

**Step 1 — Reproduce the hang (confirm T15 still happens on this commit):**

```bash

sleep 15
kubectl get isvc sklearn-iris-cached -o jsonpath='deletionTimestamp={.metadata.deletionTimestamp} finalizers={.metadata.finalizers}'
```

Observed exactly the T15 failure: `deletionTimestamp` set, `finalizers=["inferenceservice.finalizers"]` stuck. Controller logs spammed the canonical error in a tight reconcile loop:

```
admission webhook "inferenceservice.kserve-webhook-server.validator" denied the request:
update rejected: deploymentMode cannot be changed from 'Standard' to 'RawDeployment'
```

**Step 2 — Run the originally-documented 3-step workaround (scale 0 → patch → scale 1):** ❌ **FAILED.**

The patch command at step 2 returned:
```
Error from server (InternalError): failed calling webhook
  "inferenceservice.kserve-webhook-server.defaulter":
  failed to call webhook: ... context deadline exceeded
```

**Root cause discovered during retest:** Scaling the controller to 0 makes the webhook unreachable, but the webhook's `failurePolicy: Fail` causes the API server to **reject** any patch that can't reach the mutating webhook. The 3-step recipe described in the test report was a plausible-sounding fiction — never end-to-end validated until now.

**Step 3 — Tried `failurePolicy: Ignore` alone (controller up):** ❌ **FAILED.**

```
Error from server (Forbidden): admission webhook "inferenceservice.kserve-webhook-server.validator"
denied the request: update rejected: deploymentMode cannot be changed from 'Standard' to 'RawDeployment'
```

**Root cause:** `failurePolicy: Ignore` only admits webhooks that **fail to reach the server**. A webhook that **returns a deny verdict** is still denied. So flipping the failurePolicy without also making the webhook unreachable doesn't help.

**Step 4 — Corrected workaround (the GUIDE has been updated to this):** ✅ **WORKS.**

```bash
# 1. Set failurePolicy=Ignore on BOTH mutating + validating webhook configs
kubectl patch mutatingwebhookconfiguration inferenceservice.serving.kserve.io --type=json \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Ignore"}]'
kubectl patch validatingwebhookconfiguration inferenceservice.serving.kserve.io --type=json \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Ignore"}]'

# 2. Scale controller to 0 (webhooks now unreachable + Ignore = admit as no-op)
kubectl scale -n kserve deployment/kserve-controller-manager --replicas=0
kubectl wait --for=delete pod -l control-plane=kserve-controller-manager -n kserve --timeout=60s

# 3. Patch finalizers off
kubectl patch isvc sklearn-iris-cached -n default --type=merge \
  -p '{"metadata":{"finalizers":[]}}'
# → "inferenceservice.serving.kserve.io/sklearn-iris-cached patched"

# 4. Verify gone
kubectl get isvc sklearn-iris-cached -n default
# → "Error from server (NotFound): inferenceservices.serving.kserve.io \"sklearn-iris-cached\" not found" ✅

# 5. Restore: scale controller up + failurePolicy=Fail
kubectl scale -n kserve deployment/kserve-controller-manager --replicas=1
kubectl wait --for=condition=Ready pods -l control-plane=kserve-controller-manager -n kserve --timeout=120s
kubectl patch mutatingwebhookconfiguration inferenceservice.serving.kserve.io --type=json \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Fail"}]'
kubectl patch validatingwebhookconfiguration inferenceservice.serving.kserve.io --type=json \
  -p='[{"op":"replace","path":"/webhooks/0/failurePolicy","value":"Fail"}]'
```

Total elapsed: T13 → T18 = **43 seconds** (from "scale 0" to "controller back up + failurePolicy restored"). The admission-bypass window where other ISVC creates would skip KServe validation was ~30 s; in dev this is irrelevant, in production this is small enough to land inside a normal maintenance change.

**Pass criteria:**

|---|---|---|
| T15 hang reproduces on this commit | ISVC stuck Terminating | ✅ confirmed at T1 (15:32:18) |
| Originally-documented 3-step workaround fails | exposes docs gap | ✅ failed at T3 with `context deadline exceeded` |
| `failurePolicy: Ignore` alone fails (controller up) | webhook reachable + deny verdict | ✅ failed at T9 with `update rejected: deploymentMode cannot be changed` |

**Fix:** Replace the sed function with a Python YAML walk that mirrors `apply.go`'s structural rewrites (RoleBinding subjects, WebhookConfiguration service ns, Certificate dnsNames+commonName, cert-manager inject-ca-from annotations). **OR** as a short-term mitigation: remove `KSERVE_NAMESPACE` override from install.sh and document that custom-namespace requires the operator path.

### Issue #2 — Offline LocalModelCache sample uses unsupported `pvc://` URI scheme ✅ FIXED (see T14-RETEST)

**Severity:** **High** — sample ships in `06-sample-model/` and is documented in `LOCAL-MODEL-CACHE-GUIDE.md`. Users following the guide will fail.
**Where:** [`kserve-raw-base/localmodelcache-offline-sample.yaml.tmpl`](../kserve-raw-base/localmodelcache-offline-sample.yaml.tmpl) and related offline samples; [`extra-docs/LOCAL-MODEL-CACHE-GUIDE.md`](LOCAL-MODEL-CACHE-GUIDE.md) "Air-gapped flow" section.

### Issue #3 — KServe v0.16.0 upstream bug: ISVC finalizer cleanup blocked by own webhooks ✅ DOCS WORKAROUND SHIPPED (upstream still open)

### Issue #4 — `localModel.defaultJobImage` ConfigMap setting not honored at runtime ⚠️ (WORKAROUND IN PLACE — upstream still open)

**Severity:** **Medium** — image pinning we designed doesn't take effect via ConfigMap.
**Where:** Upstream KServe v0.16.0 localmodel-controller binary.
**Surfaced by:** T14.

**Symptom:** Despite the ConfigMap correctly carrying `localModel.defaultJobImage: "kserve/storage-initializer:v0.16.0"` (verified both in the embedded YAML and in the live cluster), running download Jobs that fall back to the default container use `kserve/storage-initializer:latest`. The controller's `getContainerSpecForStorageUri()` in `pkg/controller/v1alpha1/localmodelnode/controller.go:175-203` only consults `ClusterStorageContainer` instances; the ConfigMap `defaultJobImage` setting plumbing is incomplete in v0.16.0.

**Workaround in place (post-Issue #2 fix):** The shipped air-gap sample at `kserve-raw-base/airgap-localmodelcache/06-clusterstoragecontainer-s3.yaml` defines a `ClusterStorageContainer` with `workloadType: localModelDownloadJob` and explicit `image: kserve/storage-initializer:v0.16.0`. When a `ClusterStorageContainer` matches the cache's URI prefix, the controller uses ITS image, bypassing the ConfigMap-fallback path entirely. **For online (`gs://`) flows that rely on the default container,** the workaround is to ship a parallel `ClusterStorageContainer` for `gs://` with the pinned image (could be added as a one-line follow-up sample if customers report needing it).

**Fix (upstream):** File a KServe issue requesting the localmodel-controller's default-container fallback (line 197-202 of controller.go) to honor `LocalModelConfig.DefaultJobImage` from the ConfigMap. Out of scope for this branch.

### Issue #5 — LocalModelCache chown ordering on hostpath dev clusters ✅ FIXED (chown helper DaemonSet shipped)

**Severity:** **Medium** — only affects dev clusters (Docker Desktop, kind, minikube); production CSI clusters not impacted.
**Where:** [`extra-docs/LOCAL-MODEL-CACHE-GUIDE.md`](LOCAL-MODEL-CACHE-GUIDE.md) "Prerequisites → Chown" section.
**Surfaced by:** T13.

**Symptom:** A naive sequence of "chown hostpath → apply NodeGroup + Cache" fails because the `localmodelnode-agent` DaemonSet (running as root) populates `models/<cache-name>/` subdirectories AFTER the chown, leaving them root-owned. The storage-initializer (UID 1000) then can't write.

**Fix:** Update the GUIDE to prescribe the right ordering: apply CRs first → wait for agent to populate subdirs → run chown. OR: ship a sample chown-hostpath-pod.yaml template that re-runs after the cache is created. OR: instruct users to run chown twice. Also captured in memory ([`localmodel_chown_ordering.md`](/Users/akashdeo/.claude/projects/-Users-akashdeo-kserve-op/memory/localmodel_chown_ordering.md)) for future sessions.

### Issue #6 — `setup-credentials.sh` pre-flight requires OLM namespaces ✅ FIXED (see T04-RETEST)

**Severity:** **Medium** — blocks Option B (direct-manifest deploy) users when their registry is private.
**Where:** [`generate-kserve-operator.sh`](../generate-kserve-operator.sh) heredoc that emits `setup-credentials.sh`.
**Surfaced by:** T04.

**Symptom:** The script's pre-flight requires `olm` and `operators` namespaces (created by `operator-sdk olm install`). Option B users who deploy via `kubectl apply -f operator-deployment.yaml` (no OLM) fail this check and the script aborts before creating any pull secret. **Fix:** Add a `--non-olm` flag that skips the OLM-namespace checks and only creates secrets in `default` + `kserve-operator-system`. OR document the manual `kubectl create secret docker-registry ...` workaround in QUICK_START.md Option B.

### Issue #7 — `enable-ingress.sh` webhook race after controller restart ✅ FIXED (see T06-RETEST)

**Severity:** **Medium (now repeated twice — T06 + T12)** — script's prior "Issue #3 fix" is insufficient.
**Where:** [`generate-kserve-operator.sh`](../generate-kserve-operator.sh) heredoc that emits `enable-ingress.sh`.
**Surfaced by:** T06 + T12.

**Symptom:** After `enable-ingress.sh` restarts the controller, the next `kubectl apply -f sklearn-iris.yaml` fails with `failed to call webhook: ... context deadline exceeded`. `kubectl rollout status` + `kubectl wait --for=condition=Ready pods` is **insufficient** — the webhook server inside the pod needs additional startup time after Pod-Ready flips. A manual `sleep 20` resolves it.

**Fix:** Embed a webhook-probe loop in `enable-ingress.sh` (curl/openssl probe of port 9443) after the rollout-status wait, OR add an HTTP `/readyz` probe on port 9443 to the controller's readinessProbe (currently only checks port 8081). The latter is the correct upstream-style fix.

### Issue #8 — `generate-kserve-operator.sh` exits 1 after `-b` build, masking `-o` ✅ FIXED (see T08-RETEST + T09-RETEST)

**Severity:** **Medium** — misleads CI/CD; affects `-b -o` (build + bundle, no push).
**Where:** [`generate-kserve-operator.sh`](../generate-kserve-operator.sh) post-build step (likely a `set -e` interaction).
**Surfaced by:** T08 + T09.

**Symptom:** After "successfully built!" message, script exits 1. With `-b -o` (no `-p`), the bundle generation step never runs. `p-kserve-operator-package/` not created.

**Fix:** Audit the script's post-build steps under `set -e`; ensure non-fatal cleanup or status-print failures don't propagate exit code 1.

### Issue #9 — KServeRawMode CR delete is a silent UX trap ℹ️

**Severity:** **Low (design choice)** — already documented in `gaps-and-observations.md`; T17 confirms behaviour on v0.16.0.

**Symptom:** Deleting the KServeRawMode CR removes it cleanly, but the operator doesn't recreate it and doesn't tear down KServe. User must manually `kubectl rollout restart` the operator deployment to trigger auto-init.

**Fix (optional):** Log an event when the CR is deleted; document the restart workaround in QUICK_START. Or treat as a documented intentional behaviour.
