> **⚠️ New finding (T10) — Docker Hub cross-namespace blob-mount bug blocks `mirror-images.sh --load` when the destination account is only `docker login`'d (no explicit `--dest-creds`):**
>
> `mirror-images.sh --load` (and the equivalent raw `skopeo copy oci-archive:... docker://docker.io/akashdeohuf/...`) failed with `insufficient_scope` / `Failed to parse the authentication scope from the given challenge`, requesting a combined scope like `repository:akashdeohuf/kserve-raw-operator:push,pull repository:akashneha/kserve-raw-operator:pull` in a single token exchange — Docker Hub's token service cannot parse multi-repository combined scopes. This reproduced identically whether copying from an `oci-archive` file or a plain OCI `dir:` (ruling out an archive-embedded source annotation as the cause) — Docker Hub itself proposes a cross-repo blob mount from `akashneha` (source, since the content-addressed blobs are byte-identical to what's already public there) while pushing to `akashdeohuf` (destination), and the combined-scope token request is malformed. **This reproduces even though `docker login -u akashdeohuf` had already succeeded** — the failure is not a missing-credential problem, it's a registry-side auth-scope bug triggered specifically by the cross-namespace mount attempt.
>
> **Workaround:** explicit `skopeo copy --dest-creds akashdeohuf:<token> ...` (bypassing `mirror-images.sh`'s reliance on ambient `docker login` state) succeeded on the first try for both images. This suggests `mirror-images.sh --load --user <u> --pass <p>` (which builds `--dest-creds` explicitly, as originally designed) is the CORRECT invocation and was not itself broken — my initial attempt to avoid passing the PAT as a CLI arg (relying on ambient `docker login` instead) is what triggered the bug, not the script itself.
>
> **Documentation gap identified:** `generate-kserve-operator-README.md` and `mirror-images.sh`'s own header comment should note that `--load` requires explicit `--user`/`--pass` (or an interactive prompt) even if the destination registry is already `docker login`'d — omitting them and relying on ambient credentials can trigger this Docker Hub cross-namespace mount bug on real accounts with overlapping blob content. Not a kserve-op regression; a Docker Hub API quirk worth calling out for future operators of this air-gap flow.

### Phase 5 / Phase 6 infrastructure observations (worth recording)

1. **OLM bumped to v0.43.0** (latest stable). v0.29.0 release assets are no longer downloadable from GitHub. OLM is just the deploy mechanism for the bundle — version change is immaterial to the KServe controller behavior we're verifying.
2. **cert-manager v1.16.2** unchanged from v0.16 round.
3. **`setup-credentials.sh` Design D behavior:** during T01, a package built WITHOUT `--customer-registry` and a run WITHOUT `--also-workload-ns` still placed the pull secret in `default` ns in addition to `kserve-operator-system`. The v0.16 round's T22a claimed `default` was skipped under the same conditions. **Investigate during the T22a re-run.** Could be a real regression OR misleading prior memory; either way, capture the truth here.
4. **Port-forward routing quirk:** requests sent with `-H "Host: …"` header against a `kubectl port-forward` connection got URL-encoded weirdly and reached the predictor with `nan` body. Same request WITHOUT the Host header worked perfectly. Use `curl -X POST -H "Content-Type: application/json" http://localhost:8080/... -d @input.json` (no Host header) in subsequent in-cluster tests.
