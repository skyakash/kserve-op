### Phase 5 / Phase 6 infrastructure observations (worth recording)

1. **OLM bumped to v0.43.0** (latest stable). v0.29.0 release assets are no longer downloadable from GitHub. OLM is just the deploy mechanism for the bundle — version change is immaterial to the KServe controller behavior we're verifying.
2. **cert-manager v1.16.2** unchanged from v0.16 round.
3. **`setup-credentials.sh` Design D behavior:** during T01, a package built WITHOUT `--customer-registry` and a run WITHOUT `--also-workload-ns` still placed the pull secret in `default` ns in addition to `kserve-operator-system`. The v0.16 round's T22a claimed `default` was skipped under the same conditions. **Investigate during the T22a re-run.** Could be a real regression OR misleading prior memory; either way, capture the truth here.
4. **Port-forward routing quirk:** requests sent with `-H "Host: …"` header against a `kubectl port-forward` connection got URL-encoded weirdly and reached the predictor with `nan` body. Same request WITHOUT the Host header worked perfectly. Use `curl -X POST -H "Content-Type: application/json" http://localhost:8080/... -d @input.json` (no Host header) in subsequent in-cluster tests. NOT a KServe v0.17 issue.
5. **Pre-existing generator bug surfaced (not introduced by v0.17 upgrade):** `operator-sdk init` failure at `[1/4]` in `generate-kserve-operator.sh` does NOT propagate to script exit code; the script exits 0 even when scaffolding fails, leaving stale partial bundle dirs around. Workaround: always `-c p-kserve-operator` before re-running. **Future fix:** add `|| exit 1` after the `operator-sdk init` invocation. Will file separately.
6. **Docker Hub registry blob collision:** `:v500` tag had stale 2026-05-20 manifest residue causing `blob unknown to registry` push collision on retry. Adopted fresh `v17001`/`v17002` tags instead. Old stale tags left to rot on Docker Hub.

### T04 — direct `kubectl apply -f operator-deployment.yaml` (no OLM, no install.sh)

**v0.17 deviation worth noting:** Option B raw `kubectl apply` of `operator-deployment.yaml` does NOT auto-create the `kserve` namespace. The customer-facing `install-operator-deployment.sh` wrapper DOES create it (per its docs: "The target namespace either pre-created OR will be created by this"). Tests that use raw `kubectl apply` need to either pre-create `kserve` ns or wait through the auto-init backoff (which works correctly but is slow without intervention).

**Phase 5 package-contamination finding (recorded for future improvement):** my Phase 5 sequence ran 4 builds in succession (v17001, v17002, T08 v17003, T09 v17004), each overwriting `p-kserve-operator-package/` on disk with the previous one.
